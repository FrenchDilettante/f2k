# Graphics: gdi32, the screen DCs, TextOut onto the framebuffer: assumptions

Every decision taken without a capture, and every place the work order was ambiguous or departed from, one line each:
what was decided; why (the public documentation relied on, or the order's wording read); what would settle it.
"guidc:" names a line of `tests/gdi32/guidc/output.txt`; "capture" a block still to write and capture on the Windows 2000 VM.

## Deviations from the order

- No guidc block is gated: every block needs user32 (RegisterClass/CreateWindowEx, or GetDC/ReleaseDC), whose bodies the scope fence leaves to the window slices, and guidc.exe does not even load (user32's catalogue records are not exported). The pending reasons now say what each block waits for. Settles itself: the window slices serve those exports, then `pixel` should pass first (it needs GetDC(NULL) and ReleaseDC alone).
- The on-target smoke runs a new C fixture, `tests/gdi32/gditext` (CreateDCA of DISPLAY, TextOutA, colors, ExtTextOutA, DeleteDC), declared ahead of its build: no existing corpus binary creates a screen DC without user32 (guidc needs GetDC, guidisp paints nothing), and the C fixtures stay the tests (no Rust test program). Until `tests\build.bat gditext` and `capture.bat gditext` run on the VM, `tests/core/test_textout.py` and the fixture's block are skipped as awaited. Settled by: that VM trip (the fixture is declared `gate = true`, expecting F2K to pass at once).
- The path was verified on target with a throwaway Rust probe (not committed): FiSH running it painted "Hello, F2K!", "Hi", the ETO_OPAQUE "abc" box and red-on-blue text; SetPixel/GetPixel answered 0x030201; the teardown audit was clean with a DC left open; the smoke test passed with the probe standing in for gditext.exe.
- The VBE driver is touched (fenced): `PixelMemory` gained `load`, `Framebuffer` `get_pixel`, `Geometry` `rgb` (and a test-only `packed`), `with_framebuffer` is re-exported. GetPixel must read the screen, and the seam had no read; the alternative was win32k reading the LFB itself, outside the driver. Settled by: the owner's review.
- user32's spec gains three internal records (NtUserGetDC, NtUserGetDCEx, NtUserGetWindowDC), and so three unused stubs in user32.dll: the kernel's table is generated from the specs' internal records, and the order asks for those handlers. Their exports stay catalogued. Settled by: the window slices writing the GetDC bodies over them.
- gdi32's CreateDCW enters through NtGdiOpenDCW (0x10e1), a service the order does not list: with GetDC fenced it is the only way a program reaches a screen DC, and Windows 2000's gdi32 creates its DCs through it, never through an NtUser call. Settled by: nothing further (the layering is Windows 2000's).
- Services the order leaves to "whatever guidc's calls marshal to": NtGdiDeleteObjectApp (0x1075, DeleteDC and DeleteObject), NtGdiSelectBrush/Pen/Font (0x10fa/0x10fd/0x10fc, SelectObject by the object's kind), NtGdiGetDCDword (0x10a3) and NtGdiGetAndSetDCDword (0x1097, the colors and the mode), NtGdiGetTextMetricsW (0x10cb), NtGdiGetTextExtent (0x10c8): Windows 2000's own entries for those calls by name. Their argument lists are F2K's own, as every win32k service's.
- guidc: `GetTextMetricsA ... tmHeight=16 tmAveCharWidth=7` and `GetTextExtentPoint32A(hdc, "Hello", 5, &sz) ... cx=34 cy=16` disagree with the order's 8x16 answers (average 8, Hello 40). Kept the order's: the capture's numbers are Windows 2000's proportional System font's, which F2K does not have, and answering 7 while drawing 8-pixel cells would be inconsistent. The extent block's pending reason records it. Settled by: a proportional system font slice (the widths are not public documentation: a capture of GetCharWidth32 over the System font would pin them).
- The rasterizer lives in its own module, `kernel/src/win32k/raster.rs`, beside `dc.rs` (the services) and `font.rs` (the glyphs): the order names only those two files; the split keeps the host-tested drawing apart from the services.

## The DC objects

- A DC handle is a process handle-table entry (the order's design), so its value is small and a multiple of 4; Windows 2000's are GDI handles of their own table. NtClose and DuplicateHandle reach them too. Settled by: a capture of NtClose/CloseHandle on an HDC, if a program ever relies on it failing.
- A DC is made each time it is asked for (no DC cache); DeleteDC closes it, the process's end closes the rest. Settled by: GetDC/ReleaseDC's cache semantics, with the window slices.
- A DC's clipping region is the screen's extent when it is made, and empty when the graphics mode is not set yet (painting then draws nothing, SetPixel/GetPixel answer CLR_INVALID, TextOut still succeeds); creating the DC never fails for want of a mode. Windows always has a display; failing the create would break programs started before FiSH sets the mode. Settled by: nothing on Windows 2000 (a display always exists).
- The window a GetDC/GetDCEx/GetWindowDC names is ignored: every DC is the screen's (the order: "answer as a screen DC", no windows exist). DCX_ flags and the region are ignored. Settled by: the window slices.
- The pool holds 64 DCs at once; past that, CreateDC fails with STATUS_INSUFFICIENT_RESOURCES (ERROR_NO_SYSTEM_RESOURCES). Windows 2000's limit is GDI's 16K handles. Settled by: a fixture that makes many DCs.
- The DC's object type is named "Dc" for NtQueryObject's ObjectTypeInformation, and its name query is STATUS_NOT_IMPLEMENTED, as the window station's: Windows 2000 has no such object type (a DC is no kernel object there). Settled by: nothing (F2K-only).
- The DC's handle carries STANDARD_RIGHTS_REQUIRED (0x000F0000): a DC has no documented access rights.
- A DC starts with the documented defaults: text black, background white, mode OPAQUE (guidc: SetTextColor previous=0x000000, SetBkColor previous=0xFFFFFF, SetBkMode previous=2), the white brush, the black pen and the system font selected (SelectObject's documentation; guidc: SelectObject's previous non-NULL).

## The stock objects

- Every documented stock index (0-8, 10-19, DC_BRUSH and DC_PEN included) answers a constant handle, not only guidc's two: it costs nothing and GetStockObject documents them all. Index 9 and past 19 fail (NULL, ERROR_INVALID_PARAMETER). Settled by: a capture of GetStockObject over every index (Windows 2000 may answer NULL for 9 without a last error).
- A stock handle is F2K's own constant: 0x00800000 (a stock bit) | kind << 16 | index, the kind GetObjectType's (OBJ_BRUSH 2, OBJ_PEN 1, OBJ_FONT 6, OBJ_PAL 5): gdi32 reads a handle's kind from its bits, as Windows 2000's gdi32 does from its GDI handles, and no handle-table value reaches that high. Settled by: nothing (programs must not depend on handle values).
- A DC keeps one selected object per kind (brush, pen, font), not the order's one "selected stock object": SelectObject answers the previous object of the same kind (documented). Selecting a palette or a non-stock handle fails with ERROR_INVALID_HANDLE (palettes are SelectPalette's). Settled by: a capture of SelectObject with a palette and with a bad handle.
- DeleteObject of a stock object succeeds and deletes nothing (documented: "not necessary, but not harmful"; guidc: DeleteObject(the WHITE_BRUSH) ret=1). DeleteDC of a stock object's handle fails with ERROR_INVALID_HANDLE (it is no DC). Settled by: a capture of DeleteDC(GetStockObject(...)).
- DeleteObject of a DC handle deletes the DC (one service, NtGdiDeleteObjectApp, serves both). Settled by: a capture of DeleteObject(hdc).

## Colors, modes, pixels

- The colors are stored as given, the whole COLORREF (palette flags included), and answered back so; drawing uses the RGB part. Settled by: a capture of SetTextColor(PALETTEINDEX(1)) then GetTextColor.
- SetBkMode with a mode other than TRANSPARENT or OPAQUE fails with 0 and ERROR_INVALID_PARAMETER, the DC untouched (documented return 0 on failure; the error is a guess). Settled by: a capture of SetBkMode(hdc, 3).
- SetPixel answers the color set, the RGB part of the one asked for (documented: "the RGB value the function sets the pixel to"; the framebuffer is 32 bpp, so no nearest color differs; guidc: previous=0x030201). Outside the clipping region SetPixel and GetPixel answer -1 (CLR_INVALID) without touching the last error; on a handle that names no DC, -1 with ERROR_INVALID_HANDLE. Settled by: a capture of SetPixel off-screen and on a bad DC.
- A failed service sets the last error through rtl's NTSTATUS table (STATUS_INVALID_HANDLE → 6, STATUS_INVALID_PARAMETER → 87); a success leaves the last error untouched (guidc: err=- on every success). Windows 2000's gdi32 imports no RtlNtStatusToDosError, so the mapping is rtl's code linked in, not an import. Settled by: captures of the failure paths.

## Text

- One font for every DC whatever font is selected: the 8x16 VGA bitmap (code page 437's repertoire), taken as data from QEMU's standard VGA BIOS image (the classic VGA font's bitmaps, public font facts). A wide character maps to its glyph through code page 437 (rtl::codepage): ASCII as is, the page's upper half and its control-byte glyphs by their Unicode characters, a best fit for Latin letters with diacritics, `?` otherwise; 0x00-0x1F draw the page's control glyphs. Settled by: a real system font slice.
- (x, y) is the cells' top left (TA_TOP | TA_LEFT, the documented default alignment); the alignment and the current position (TA_UPDATECP) are not served. Settled by: a SetTextAlign fixture.
- OPAQUE fills each glyph's 8x16 cell with the background color; with advances (lpDx) wider than 8 the gaps between cells are not filled. Windows fills the text's whole bounding box. Settled by: a screenshot comparison of ExtTextOut with lpDx under OPAQUE.
- ExtTextOut's ETO_OPAQUE fills its rectangle with the background color whatever the background mode (documented: "the current background color should be used to fill the rectangle"); ETO_CLIPPED clips to it; both need a rectangle (none: ignored). A rectangle is used as given (not normalized). Other options (ETO_GLYPH_INDEX, ETO_RTLREADING...) are ignored. Settled by: a capture of ExtTextOut with an inverted rectangle and with ETO_GLYPH_INDEX.
- TextOutA/W and GetTextExtentPoint32A/W with a negative length fail with ERROR_INVALID_PARAMETER before any service; a zero length succeeds. Settled by: a capture of TextOutA(hdc, 0, 0, "x", -1).
- The narrow forms convert through ntdll's RtlMultiByteToUnicodeN (in gdi32's import table), a character per byte (code page 1252 is single-byte), so ExtTextOutA's lpDx keeps its meaning; strings past 256 bytes convert into a block of the process heap (RtlAllocateHeap, imported too).
- CreateDCA converts the driver's and the device's names (up to MAX_PATH, longer: ERROR_INVALID_PARAMETER); the output name and the DEVMODE are ignored. CreateDCW takes the DISPLAY driver (any case) with or without a device name, or no driver and a device name; the kernel accepts the primary display alone (a null device or `\\.\DISPLAY1`), another device failing with ERROR_INVALID_PARAMETER; another driver (a printer's) or no names at all go to the stub routine (NULL, ERROR_CALL_NOT_IMPLEMENTED, a COM1 line). Settled by: a capture of CreateDC(NULL, "\\\\.\\DISPLAY1", ...) and of CreateDC("DISPLAY", "\\\\.\\DISPLAY2", ...).
- TEXTMETRIC: height 16, average width 8, overhang 0, every other field 0 (the order's "the rest zeroed"), so tmAscent, tmMaxCharWidth, tmWeight, tmFirstChar... read 0. GetTextMetricsA converts the four characters (all 0) through RtlUnicodeToMultiByteN; a null structure fails with ERROR_INVALID_PARAMETER. Settled by: a capture of every TEXTMETRIC field of the System font (then the real values replace the zeros).
- TEXTMETRICA/W laid out as wingdi.h's on x86: 56 and 60 bytes, the padding after tmCharSet made an explicit field. Settled by: nothing further (public header layout).
- NtGdiEngTextOut (0x1257) is served by ExtTextOutW's handler with ExtTextOutW's arguments (the order: "collapses into the same handler"); gdi32 has its stub but never calls it. Settled by: the display-driver side, if F2K ever loads one.
- GetTextExtentPoint32 reads the whole string (a fixed-pitch font needs only its length), so a string the caller cannot read fails as on Windows. Settled by: nothing further.
